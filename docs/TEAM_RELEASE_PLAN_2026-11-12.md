## Most urgent fixes in progress

**Legacy GUI correction:** The optional Windows setup wizard was a second, unsupported configuration path: it wrote ignored environment names, overwrote the Wazuh XML example, started Uvicorn on all interfaces, and claimed full provisioning. It now only opens the maintained `terminus-setup` CLI after the operator clicks, from a checked source folder. It does not write configuration or start the API itself. One focused handoff test, targeted Ruff, and targeted Basedpyright pass; a packaged GUI build and manual click-through remain unverified.

**Presentation launcher correction:** `run_demo.bat` previously deleted operational incident and workflow rows before checking the server and could bind Uvicorn to all interfaces. It now delegates to the existing isolated bank/SOC rehearsal, which creates a separate temporary database and binds loopback. The synthetic traffic helper no longer purges records, accepts only explicit loopback origins, and refuses redirects so demo session tokens cannot follow them. Seven focused network tests pass. The revised one-click batch flow has not had a manual presentation run on this PC.

1. Remove scripted threat conclusions from normal operation. Show when analysis is offline, model-assisted, or only a fixture; keep missing or conflicting evidence visibly unknown.
2. Remove generated “live traffic,” inferred protection labels, and approval messages that imply containment before an effect check.
3. Require a source-bound credential for genuine Wazuh intake. Keep manually submitted synthetic alerts clearly separate.
4. Make startup and setup truthful: no presentation data in operational mode, localhost default, supported SQLite configuration, and visible worker readiness.
5. Keep consequential actions limited to the exact tested lab scope. Show requested, authorized, dispatched, independently effective, and recovered as distinct states.

## Go/no-go gates

**The disposable-lab demo may be called a GO only if** a fresh install reproduces the exact scenario; every synthetic or scripted item is labeled; one genuine, source-authenticated Wazuh alert has raw IDs and timestamps; conclusions cite collected evidence or say unknown; a separate authorized temporary block is independently observed; management access remains healthy; and expiry/undo is independently observed. Denied approval, protected IP, missing sensor, worker interruption, duplicate delivery and unverifiable effect must fail visibly and safely. Preserve raw, redacted artifacts. If any gate fails, present it as a prototype with the failed gate listed.

The [fresh-lab acceptance procedure](LAB_ACCEPTANCE.md) is included with the source ZIP. A fresh extracted API install has passed; the complete Wazuh scenario has passed once on the existing lab and still needs repetition from the extracted copy.

**A useful pilot** additionally needs repeated analyst decisions that are measurably better or faster than Wazuh alone, durable handoff, health monitoring and restored state after restart. Generated report snapshots and campaign assignments now persist in SQLite; empty reports no longer claim healthy telemetry. Campaign restart, duplicate and tenant isolation have fixture coverage, while multiworker and backup/restore acceptance remain open. **Production-facing release** further needs tenant and role review, reliable worker supervision, backup/restore, capacity limits, deployment hardening, incident runbooks, repeated lab acceptance and representative operational results. No date or grade should override these gates.

## VPS decision

**An external disposable VPS is now the preferred path for the repeat lab run.** The local Docker lab ran the source, target, attacker and observer on a private network. During an earlier backend rerun, C: fell to about **0.02 GB free** and produced SQLite disk-full errors. The project checkout and release files are on F:, test temporary files and package caches are on D:, and Docker's WSL image was moved from an exFAT path on F: to an NTFS path on D:. That moved Docker image currently occupies **75.69 GB on D:**. Earlier fresh-install copies and test data were estimated at **1.8 GB on D:**. Three later measured smoke-test folders use another **1.4 GB**. Automatic approval review rejected recursive cleanup of both groups, so they remain. Windows and Docker Desktop still use C: for runtime data; the exact cause of the remaining C: usage is unproven. After the PC restart on November 14, the target was stopped while the Wazuh services auto-started; the worker repeatedly reported “independent lab baseline unavailable,” and sent no block. Docker Desktop and the lab were stopped. The latest D: check showed **8.24 GB free**; the most recent separate checks showed about **0.99 GB on C:** and **225.72 GB on F:**. D: is healthy NTFS but does not have the 100 GB reserved capacity recommended for the complete repeat lab. F: has the capacity, but is exFAT, Windows marks the volume dirty and its health as Warning; a read-only `chkdsk F:` found directory corruption in `\Games\Fortnite\.egstore\bps\f\` before the scan was stopped. The physical USB disk itself reported Healthy. Do not put Docker's WSL image on F: or run another full local Wazuh cycle until the file system is repaired and checked, a suitable NTFS data volume is available, and C: has several GB of headroom.

The user chose another student VPS over the local-space or Azure path and declined payment-card verification. The [current GitHub Student Developer Pack cloud listings](https://education.github.com/pack?tag=Cloud) do not establish a second student VPS offer that meets [Wazuh's 4-core, 8-GB, 50-GB single-node Docker requirement](https://documentation.wazuh.com/current/deployment-options/docker/wazuh-container.html). **The best card-free student lead is instructor-issued Google Cloud education credit:** [Google's faculty program](https://cloud.google.com/edu/faculty) lists up to $50 per student, and its [redemption guide](https://docs.cloud.google.com/billing/docs/how-to/edu-grants) says an approved instructor sends a school-email verification link and coupon. The instructor must confirm the class is eligible and the credit is available; the amount may only cover a short lab run. Google's separate [new-customer Free Trial](https://docs.cloud.google.com/free/docs/free-cloud-features) requires a payment method and is excluded. [AWS's new Free plan](https://aws.amazon.com/start-here/) usually permits signup without a card, but [its listed EC2 Free Tier instance types](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-free-tier-usage.html) are below the Wazuh size; AWS Educate provides temporary instructional labs rather than a verified persistent Wazuh host. [Oracle Always Free A1](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm) covers up to 2 OCPUs and 12 GB RAM, below the cited CPU recommendation. No cloud account or resource has been created. A school-provided lab VM is another possibility to verify with the instructor. Before any disposable Linux VM is created, the account owner must confirm at least 4 cores, 8 GB RAM and 50 GB storage, permitted Docker/system settings, SSH access, quota and zero-cost terms. Restrict SSH to an approved source and keep Wazuh and TERMINUS management ports private; delete the VM after the lab run.
